## Findings to act on

No 🔴 Must.

1. 🟡 Should — authenticated API answers carry no `Cache-Control` (SEC-01). Seen: `GET /api/libraries`, `/users`, `/auth/events`, `/profiles/:id/progress` return no `Cache-Control` header (nor does Caddy add one). Expected: `private` with `no-cache`, or `no-store`, so a shared cache or a back-forward cache after sign-out cannot show another person's data (the owner list holds usernames, last sign-in, client addresses). Repro: `curl -sk -I -b <session cookie> https://popcorntv.localhost:8443/api/libraries`. Suggested fix (not applied), in the existing `onSend` hook of `apps/server/src/app.ts`:
   ```ts
   if (!reply.hasHeader('cache-control')) reply.header('cache-control', 'private, no-cache');
   ```
   (keep the explicit cache headers of artwork and media). A new issue is needed (`fix(security): mark authenticated API answers private`); not filed by this run.
2. 🟡 Should — the web build is served without `frame-ancestors` / `X-Frame-Options`, `Permissions-Policy` and `Cross-Origin-Opener-Policy`, and without CSP (SEC-01). CSP and `frame-ancestors` are already #46 (known, not refiled); recommend adding `X-Frame-Options: DENY`, `Permissions-Policy` (camera, microphone, geolocation off) and COOP `same-origin` to the scope of #46 and to the §5 Caddy recipe. Partly mitigated today by `SameSite=Lax` (the cookie is not sent in a cross-site frame). Caddy lines:
   ```caddyfile
   header X-Frame-Options "DENY"
   header Permissions-Policy "camera=(), microphone=(), geolocation=()"
   header Cross-Origin-Opener-Policy "same-origin"
   ```
3. 🔵 Nice — a second reset link replaces the first and a role change revokes a pending reset, but neither writes a `reset_revoked` event; only the explicit `DELETE /users/:id/reset` does. Spec R9 lists "invitation and reset issue and revocation". Expected: one `reset_revoked` row per revoked link. Repro: issue two reset links for one user, read `GET /auth/events`. (Distinct from #85, which is about the actor column.)
4. 🔵 Nice — an authenticated request to an unmatched route returns the Fastify default body `{"message":"Route GET:/nope not found","error":"Not Found","statusCode":404}` (also 431), not the spec §6 shape `{ error: 'not_found' }`; it echoes the path. Repro: `curl -sk -b <session cookie> https://popcorntv.localhost:8443/api/nope`. Suggested fix: `app.setNotFoundHandler((_req, reply) => reply.code(404).send({ error: 'not_found' }))` and an `onError` mapping for 431.
5. 🔵 Nice — `GET /api/health` is public through Caddy and returns the server `version`. Expected: the version is not needed from the internet. Suggested fix: Caddy `respond /api/health 404` (the container HEALTHCHECK hits Fastify directly) or drop `version` from the public answer.

Informational (no action proposed):
- The 30-per-IP failure limit also blocks correct sign-ins and redeems from that address for 15 minutes (spec R8, verified `429` for the owner's correct password); behind one NAT or one CGNAT address, a stranger can block everyone there. Accepted by the spec; related to #72.
- `Sec-Fetch-Site: same-site` is accepted by R7 as written; the `Origin` check still blocks a sibling-origin POST. A `POST` / `DELETE` with `content-type: application/json` and an empty body answers `400 invalid_request` (Fastify default); the web client does not do it.
- "Replay while locked" and the redeem path share the per-IP counter: a visitor spamming a wrong token can lock the sign-in of everyone on the same address (same remark as above).
