## Findings

1. No Must.
2. 🟡 Should — Focus is lost after switching profile, picking a profile and confirming a delete (A11Y-01) -> F1.
   Seen: `document.activeElement` is `BODY` after each of these. Expected: move focus to the new view's heading
   (or the first profile button) and, after delete, to the next row / "Add" field. Fix: `autoFocus` / a ref focus in
   `ProfilePicker`, `ManageProfiles` after `onChanged`.
3. 🟡 Should — No security headers on the API (SEC-01) -> F4. Pre-existing; register `@fastify/helmet` (nosniff,
   referrer-policy, frame-ancestors) and `Cache-Control: no-store` on profile routes. Not caused by #10.
4. 🟡 Should — The delete confirm cannot be cancelled: Escape, blur and Tab leave "Delete X and their history"
   armed (`confirming` in `ProfileRow` is never reset); a later stray click deletes the profile and its history. Also
   the longer label wraps to its own row and shifts the layout (05-delete-confirm.png). Suggested fix: reset
   `confirming` on blur / Escape or add a "Cancel" button, keep the label short. (FON-09 / USA-04.) -> F5
5. 🔵 Nice — Error message not cleared when the user edits the field, no `aria-invalid`, and a whitespace-only
   name is sent to the server (400) instead of being caught client-side (`required` does not trim) -> F2.
6. 🔵 Nice — Touch targets 40-42 px on phone, below the 44 px house floor (A11Y-05) -> F3.
7. 🔵 Nice — Manage screen: the colour is a bare `<select>` of words ("red") with no swatch preview.

No backlog issues were filed from this run (the caller owns `gh`); F1..F5 are proposed titles:
`fix(web): move focus after profile switch/pick/delete`, `chore(server): add security headers`,
`fix(web): make the profile delete confirm cancellable`, `fix(web): clear stale profile error and validate trimmed name`,
`chore(web): raise profile form targets to 44 px`.
