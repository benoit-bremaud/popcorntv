# Issue #308 — progressive playback through the existing player

The built PopcornTV player decoded an incomplete synthetic cache through a verified-input experiment; overall feasibility remains **PARTIAL**.

## Scope

The owner authorized stage 3 after the real-backend and NordVPN experiments. This run uses
the production web bundle, the real Fastify application/routes, SQLite repositories,
authentication, library scanning, FFmpeg HLS output, subtitle extraction, hls.js and Chromium.
Only the source writer and the injected FFmpeg input boundary are experimental.

No production TypeScript, HTTP route, application configuration or deployed service changed.
The server still supports complete local media files; this harness does not enable incomplete
files in a real library or make a wishlist title ready to watch.

## Setup and safety boundary

- Node 22.23.4, FFmpeg/ffprobe 8.0.1-3ubuntu2, installed Playwright Chromium.
- Existing application build; an ephemeral SQLite database and randomly authenticated synthetic owner.
- Thirty-second 320×180 H.264 MP4, two synthetic AAC tracks tagged eng/fra and one embedded French cue.
- Complete control file scanned first, then replaced with a preallocated cache before any playback session.
- Known reference producer writes 16 KiB ranges at 125 ms intervals, approximately 2.5 times average media consumption.
- Every range is independently read back against the reference before extending verified coverage.
- The experimental adapter accepts exactly the known synthetic input, rejects resumes/foreign paths,
  changes only the input to `pipe:0`, and retains the production output/audio/demuxer restrictions.
- FFmpeg reads at most 16 KiB at a time; missing coverage waits with a bounded timeout. A mismatch,
  cancellation, failed spawn or watchdog stops the reader and child. Cleanup awaits owned child work.
- A loopback-only HTTP transport serves the existing built assets and forwards `/api` to real Fastify
  injection. API responses are not mocked. This transport is not the production Caddy/TLS deployment.

The complete control's probe supplies the known fixture metadata. This is not proof that an arbitrary
partial download has enough metadata to scan safely. Synthetic sine waves and language tags test
selection plumbing; they do not establish spoken-language correctness.

## Automated verification and coverage

Eleven fast tests exercise the observation predicates, CLI opt-in/error serialization, input confinement,
audio/output preservation, verified feeding/backpressure, corrupt cache refusal, missing coverage timeout,
session-handle cancellation, whole-adapter shutdown, watchdog, failed spawn and bounded stderr retention.
Only OS/process/DOM boundaries are doubled. Two opt-in real browser scenarios exercise normal completion
and cancellation; they are not substituted with mocked player responses.

|---|---:|

| Branches | 94.74% |

No coverage exclusion directive is used. Remaining uncovered lines are the direct executable
entry; the CLI function itself has success, refusal and secret-free failure tests, including
the real nominal browser journey through its default executor. Remaining function gaps are
browser-error and stdin-error diagnostic callbacks, which were not deliberately triggered by
these scenarios. No 100% claim is made for this new module.

All seven exported functions carry contract documentation. Non-obvious decisions explain why input
protocol changes remain experiment-only, why a full-file baseline precedes cache replacement, why
the independent cache check prevents stale-poll false positives and why subtitle readiness is separate.
No production API route was added; the existing API contracts remain unchanged.

## Reproduction

Build the application first (`pnpm build`) and use Node 22+ with the already installed browser and
FFmpeg/ffprobe. No downloader, VPN credential, TMDB key or real media file is required here.

```sh
# Fast boundary tests only:
node scripts/player-spike.test.mjs

# Complete local experiment and coverage ratchet:
node --experimental-test-coverage \
  --test-coverage-include='**/scripts/player-spike.mjs' \
  --test-coverage-lines=98 \
  --test-coverage-branches=94 \
  --test-coverage-functions=94 \
  scripts/player-spike.test.mjs --browser

# Nominal experiment alone, JSON result on stdout and structured diagnostics on stderr:
node scripts/player-spike.mjs --run
```

The harness is opt-in and is not silently included in workspace Vitest commands. Logs include actual
application playback/session/request events, cache progress milestones, source errors, child startup/exit,
first frame, normal end, cancellation and cleanup. The CLI never prints raw exception messages;
credentials remain covered by the application's existing logger redaction.

## Application regression checks

Local build, typecheck, ESLint and formatting checks passed. The workspace coverage run passed
57 shared and 814 server tests (7 existing server tests skipped). Its web run exposed a timing
failure in the existing Discover-to-catalog dialog test: the accessible dialog query reached its
deadline before React's modal effect had finished under the combined workload. The test now
awaits the resolved load and modal effects through async `act`, then asserts synchronously;
no arbitrary sleep, timeout increase or retry was introduced. Its 31-test file and the complete
485-test web coverage suite passed after the change, committed separately in `8ca4834`.

Application line coverage remains shared 100%, server 98.4%, web 98.96%. This evidence is not
a complete pre-push/release gate: the existing skipped tests, Sonar, independent adversarial
review and deployment QA are not silently treated as passed. No push, merge or deployment occurred.

## Next gate

This run proves the existing HLS/player path can consume a carefully verified progressive pipe.
It does not connect the real qBittorrent transfer and browser in one run, prove captions available
at startup, or exercise progressive direct play, seeks beyond coverage, resumed partial input,
completion/import rename, arbitrary containers, unexpected VPN failure or Pi limits.

Keep #308 open and the verdict PARTIAL. The next evidence must combine real backend telemetry,
safe cache reads and this actual player, with an explicit language/subtitle preparation gate.
Production readiness policy and player integration still belong to their planned implementation bricks.
